# Talent-string decoder investigation (2026-07-13)

## Goal

Decode a real in-game talent-loadout export string (the `talents=` value
in a `/simc` paste, or COMBATANT_INFO's talent block) into simf's flat
`frozenset[str]` of modeled talent names, so "your talents, explained"
can show a player's REAL selections instead of a nearest-match guess
against 4 hand-curated presets.

## What's solid

- **Talent-tree structural data**: `data/talent_trees/protection_warrior.json`,
  generated by `scripts/fetch_talent_tree.py` from Blizzard's own Game Data
  API (`/data/wow/talent-tree/850/playable-specialization/73`) — the
  authoritative source (confirmed live: class_talent_nodes=41,
  spec_talent_nodes=68, hero_talent_trees=[Slayer(60), Mountain Thane(61),
  Colossus(62)], each 14 nodes with ~28 of the 42 raw hero-tree listings
  actually the SAME node shared across 2 trees — deduplicated in the
  generator). Cross-checked against SimC's `trait_data.inc` (`midnight`
  branch) for 4 known talents (node_id + spell_id agree exactly:
  Reinforced Plates 90368/382939, Brutal Vitality 90451/384036,
  Thunderlord 90308/385840, Phalanx 110411/1269312 — the last one via SimC
  only, since Blizzard's API doesn't expose Apex Talent data yet, a
  Midnight-specific system; `phalanx` is the one modeled talent NOT
  reachable from the Blizzard-sourced tree JSON, named as a known gap).
- **COMBATANT_INFO entry-id join**: `entry_id_to_modeled_talent` in the
  same JSON, sourced from SimC's `trait_data.inc` (the only source found
  that exposes `id_trait_node_entry` — the id a real combat log actually
  carries — alongside spell_id in the same row). Verified BYTE-FOR-BYTE
  against a real log: `grep '(90368,112235,2)' examples/WoWCombatLog-
  050626_153703.txt` — 90368 is Blizzard's own node id for Reinforced
  Plates, 112235 is SimC's `id_trait_node_entry` for the same talent, and
  this exact triple appears verbatim in a real ACL-on COMBATANT_INFO line.
  This join is a plain set-membership lookup — **order-independent** — so
  it does not depend on any of the unresolved ambiguity below.
  `io/talent_decoder.decode_combatant_info_entry_ids` uses this and is
  fully reliable.

## What's NOT solid: the talents= string's per-node content section

Header decodes reliably: `io/talent_string_codec.decode_header` was tested
against BOTH of Brutoh's real strings (`examples/brutoh.simc` and
`examples/Brutoh Protection 2026-07-08-vault.txt`) and both produced
`version=2, spec_id=73` — spec_id landing exactly on Protection Warrior
on two independent strings is strong evidence (≈1/65536 coincidence odds
per string) that the bit order (LSB-first per base64 char, standard
`A-Za-z0-9+/` alphabet, chars concatenated in string order) and header
field widths (8-bit version, 16-bit spec, 128-bit tree hash) are correct.
This was verified against Blizzard's own shipped addon source — not
inferred — fetched from `github.com/tomrus88/BlizzardInterfaceCode`
(`Blizzard_ClassTalentImportExport.lua` + `ExportUtil.lua`, both the
original 10.0-era version and the current hero-talent-era version, now
under `Blizzard_PlayerSpells/ClassTalents/`).

Content section (per-node `is_selected → is_partial(+rank) →
is_choice(+index)` bits) does NOT decode cleanly. Symptoms: implausible
rank values (12, 24, 44, 50 — no real talent has more than 2 ranks),
implausible/contradictory choice selections, and a bit-position EOF or
large leftover-bit count depending on candidate node list — starting
almost immediately after the header (as early as the first node in
ascending-id order).

### What was tried and ruled out

1. **Bit order within a base64 char** — MSB-first gives a categorically
   worse header decode (`version=80, spec_id=130`); LSB-first is right.
2. **Node candidate list composition** — tried, in order: (a) Protection-
   only spec+hero rows from SimC (117 nodes), (b) all-Warrior-specs
   class+spec+hero rows from SimC (208 nodes — this number exactly
   matched Blizzard's own reported "208 nodes" for the bare
   `/talent-tree/850` resource, a strong independent cross-check that the
   node SET itself is right), (c) Blizzard's live API-reported Protection-
   scoped set (41 class + 68 spec + all 3 hero trees raw = 151, then
   deduplicated to 123 after finding ~28 nodes double-counted across
   shared hero trees). None produced a clean decode.
3. **Tiered-vs-choice misclassification** — found and fixed a REAL bug:
   3 nodes (Master of Warfare, Phalanx, Rampaging Berserker) are
   `node_type=1` ("tiered", a 3-rank progressive talent split across 3
   descriptive rows in SimC's data) but a naive "differing selection_index
   ⇒ choice node" heuristic wrongly classified them as 3-way choices.
   Fixed in the extraction logic. Did not resolve the early-node
   corruption (these 3 nodes sit near the highest node IDs, not the
   start).
4. **Duplicate hero-tree node listings** — found and fixed a REAL bug:
   Warrior's 3 hero trees (Slayer/Mountain Thane/Colossus) share ~28 of
   their 42 raw node listings (a node can belong to 2 of the 3 trees'
   displayed lists). Naively concatenating all 3 trees' listings double-
   counted these, consuming extra phantom bits. Deduplicating by node_id
   (keep first occurrence) reduced the corruption but did not eliminate
   it (still `bad≈50/41` selected-node reads).
5. **Header width variants** — brute-forced the "tree hash" field width
   from 0 to 200 bits (in case "optional" meant variable-length, not
   fixed-128-but-omittable) against the class+spec+hero-selector 117-node
   candidate list, scoring each width by fewest implausible rank/choice
   reads. No width produced a clean result; 128 (the documented value)
   remained among the least-bad options, consistent with it being correct
   and the real bug being elsewhere.
6. **Manual bit-math sanity check** — hand-traced the first 8 bits of the
   real string character-by-character against the programmatic decode;
   matched exactly (version=2), ruling out a bit-reader implementation
   bug in this project's own code.

### Leading hypothesis, unconfirmed

Both fetched Lua source versions carry the identical "WoW 10.0 Class
Talent Tree Import/Export" header comment verbatim, despite the code
itself changing between them (the current version's `isChoiceNode` check
gained an `Enum.TraitNodeType.SubTreeSelection` case the 10.0 version
didn't have) — meaning Blizzard's own written spec was never updated for
the hero-talent (or Apex-talent) era, even though the implementation was.
The most likely remaining gap is some structural difference in exactly
which nodes `C_Traits.GetTreeNodes` includes and in what order once hero
sub-trees and Apex talents are involved, that isn't described in either
version of the comment and wasn't reverse-engineerable from the data
sources checked here (Blizzard's Game Data API, SimC's `trait_data.inc`,
a third-party Python re-implementation of the codec). A live decode
against a tool KNOWN to work correctly today (Wowhead's calculator,
Raidbots, or an addon like `LibTalentTree-1.0` running in-client) would
settle this quickly but wasn't available in this investigation (Wowhead's
calculator is fully client-rendered with no fetchable JSON; no in-client
addon environment was available).

## Decision

Ship what's proven:

- The tree data (`data/talent_trees/protection_warrior.json`) — useful
  standalone for Phase 2 regardless of the string-decode gap.
- `decode_combatant_info_entry_ids` — real, validated improvement: any
  character loaded from a combat log now shows its REAL selected talents
  instead of a preset-name guess.
- `decode_simc_talent_string` — returns `ok=False` honestly rather than
  guessing. `simc_import.py`'s existing preset-name-match fallback stays
  exactly as it was before this investigation for SimC-paste-loaded
  characters — not a regression, just not yet the improvement originally
  hoped for on that specific path.

## Next steps (for whoever picks this back up)

- Try decoding a KNOWN-GOOD string (e.g. one Wowhead's calculator or
  Raidbots can round-trip) to get a byte-for-byte ground truth to diff
  against, rather than working purely from "does this look plausible."
- Check whether `C_Traits.GetTreeNodes` for a hero-talent-inclusive config
  returns hero-tree nodes for BOTH candidate hero trees unconditionally,
  or only the currently-selected one (this investigation assumed the
  former per the encoder's blanket iteration, but couldn't confirm against
  live client behavior).
- Consider whether Apex Talents (Phalanx's 4-point cluster, missing from
  Blizzard's public API entirely as of this check) get their own bits in
  the stream, appended or interleaved separately from the main spec-tree
  loop — the fetched Lua source predates Apex Talents entirely and may
  not describe them at all.
